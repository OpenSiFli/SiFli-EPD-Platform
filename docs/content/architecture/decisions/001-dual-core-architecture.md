# ADR-001: 双核架构与任务分工

## 状态

已采纳

## 背景

SiFli SF32LB57 提供了异构双核硬件架构：主核 HCPU 和协处理核 ACPU。在设计墨水屏阅读平台时，我们面临如何充分利用双核资源、平衡性能与复杂度的选择。

电子书阅读场景的关键特征：

1. **计算密集**：文档解析（EPUB/MOBI）、字体渲染（TrueType 测量与字形生成）、分页排版、页面像素合成
2. **交互敏感**：用户期望点击后快速响应，翻页流畅
3. **内存受限**：嵌入式设备的 PSRAM 资源有限（总计 16 MiB）
4. **异步流水**：当前页显示的同时，后台可预备邻近页面

单核方案的局限：
- 计算任务阻塞界面线程，导致触摸响应延迟
- 页面合成与用户交互争抢 CPU 时间
- 难以在保持交互流畅的同时完成复杂的文档处理

## 决策

**采用异构双核架构，按职责明确分工：**

| 核心 | 主要职责 | 典型任务 |
| --- | --- | --- |
| **HCPU** | 交互、I/O、服务管理 | 触摸事件、LVGL 界面、文件读写、网络请求、蓝牙、音频播放、应用生命周期 |
| **ACPU** | 计算密集型算法 | 文档解压解析、字体测量与字形生成、分页排版、图像解码、页面像素合成、音频编解码 |

**核心协作原则：**

1. **接口统一**：ACPU 算法通过计算组件框架接入，使用 `OPEN → STEP → CLOSE` 生命周期
2. **数据交接**：通过共享缓冲传递输入输出，HCPU 拥有文件句柄和 LVGL 对象，ACPU 只处理数据
3. **资源请求**：ACPU 需要文件数据时暂停算法，请求 HCPU 供数后从原位置继续
4. **生命周期隔离**：HCPU 管理资源所有权，ACPU 私有上下文在会话结束时释放

## 理由

### 性能优势

1. **流水并行**：HCPU 处理交互和下一次请求的同时，ACPU 继续完成上一页的计算
2. **响应速度**：触摸和按键由 HCPU 立即响应，不受 ACPU 计算影响
3. **预备能力**：当前页显示后，ACPU 持续准备邻近页面的字形和像素

### 资源隔离

1. **内存分区**：两核分别拥有独立的 PSRAM 分区，ACPU 算法内存不挤占 HCPU 界面资源
2. **故障隔离**：ACPU 计算错误可上报 HCPU 处理，不直接导致界面崩溃
3. **电源协调**：休眠前先停稳 ACPU 计算，恢复时先恢复 ACPU 环境再放开调度

### 扩展性

1. **组件化接入**：新算法只需实现组件协议，无需修改核间通信层
2. **可选卸载**：某些算法（如 Anyka 3A 音频处理）可在不支持的板型上禁用
3. **版本演进**：组件协议支持版本协商，HCPU 和 ACPU 固件可分别更新

## 后果

### 正面影响

- **交互流畅**：触摸响应延迟降低，界面操作不受文档计算影响
- **阅读体验**：打开书籍 5 秒内显示上次阅读页，翻页准备目标 1-3 秒
- **资源利用**：双核并行工作，整体吞吐量提升

### 负面影响与应对

1. **复杂度增加**
   - 需要维护核间通信协议和组件注册表
   - 应对：统一计算接口（`src/platform/epd_compute.h`）封装细节

2. **调试难度**
   - 双核问题定位需要跨核日志和状态追踪
   - 应对：提供资源请求追踪、会话状态查询、超时与取消机制

3. **资源约束**
   - 共享缓冲需要遵循对齐和缓存同步规则
   - 应对：统一缓冲管理接口，明确所有权转移时机

4. **电源管理**
   - 休眠和恢复需要协调两核状态
   - 应对：计算调度提供休眠保护，电源回调等待计算停稳

## 替代方案

### 方案 A：单核 + 协作式多任务

所有工作在 HCPU 上通过优先级调度完成。

**优点**：
- 实现简单，无核间通信开销
- 调试和内存管理更直接

**缺点**：
- 计算密集任务仍会影响交互响应
- 无法充分利用 ACPU 资源
- 文档转换和页面合成会阻塞界面

**未采纳原因**：交互体验无法满足目标，硬件资源浪费。

### 方案 B：双核 + 完全自治的 ACPU

ACPU 拥有独立文件系统访问和内存管理。

**优点**：
- 两核更彻底地并行工作
- ACPU 可独立读取文件，减少核间通信

**缺点**：
- 文件系统需要支持并发访问或双重挂载
- 内存分配策略复杂，难以动态平衡两核需求
- 存储会话、文件版本需要跨核同步

**未采纳原因**：当前 SDK 和文件系统不支持跨核并发访问，实现成本高。

### 方案 C：对称多核 (SMP)

将两核视为对等计算资源，由 RTOS 统一调度任务。

**优点**：
- 应用层无需关心任务运行在哪个核
- 负载自动平衡

**缺点**：
- RT-Thread 在当前 SDK 版本不支持 SMP
- 界面任务和计算任务特征差异大，统一调度收益有限
- 失去专核专用的资源隔离优势

**未采纳原因**：RTOS 不支持，且异构任务特征不适合 SMP 模型。
