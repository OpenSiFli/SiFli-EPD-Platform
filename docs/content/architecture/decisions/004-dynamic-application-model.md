# ADR-004: 动态应用模型

## 状态

已采纳

## 背景

平台需要支持书架、天气、AI 对话、笔记、音乐等多个应用。在设计应用架构时，面临两种典型方案：

1. **静态编译**：所有应用编译到固件中，一起烧录
2. **动态加载**：应用独立打包，可安装、卸载、更新

关键考虑因素：

- **用户需求差异**：不是所有用户都需要全部应用（如不用笔记、不听音乐）
- **更新灵活性**：应用 bug 修复不应强制更新整个固件
- **存储受限**：内部 Flash 只有 4.625 MiB 可用（`fs_root`），TF 卡可扩展但不总是插入
- **开发模式**：多人协作开发不同应用时，希望减少固件构建冲突
- **硬件能力**：RT-Thread 支持动态模块加载

## 决策

**采用动态应用模型，以 `.sap` 包分发应用**

### 核心设计

1. **应用格式**：`.sap`（SiFli Application Package）
   - 包含主模块（ELF 格式的可加载共享对象）
   - 可选私有库
   - 资源文件（图标、字符串、配置等）
   - 清单文件（`manifest.json`）：版本、依赖、权限、入口点

2. **安装位置**：
   - 内部存储：`/flash/apps/<id>/`
   - TF 卡：`/sdcard/.epd/apps/<id>/`
   - 预装：构建时打包到文件系统镜像

3. **地址空间**：
   - 动态模块与 HCPU 固件**共享地址空间**
   - 通过符号绑定使用平台导出的接口
   - 不同应用的代码段在同一地址空间内不同位置

4. **生命周期管理**：
   - 安装器负责验证、解包、登记
   - 装载器负责 ELF 加载、符号解析、模块引用计数
   - 受管服务框架负责后台任务和资源回收

### 应用与平台的接口边界

```
┌─────────────────────────────────────────────────┐
│          动态应用 (.sap)                         │
│  ┌─────────────────────────────────────────┐   │
│  │  应用代码 (ELF 共享对象)                 │   │
│  │  - UI 页面实现                           │   │
│  │  - 业务逻辑                              │   │
│  │  - 数据处理                              │   │
│  └───────────────┬─────────────────────────┘   │
│                  │ 通过符号调用                 │
└──────────────────┼─────────────────────────────┘
                   │
┌──────────────────┼─────────────────────────────┐
│                  ↓                              │
│         平台导出接口 (符号表)                    │
│  ┌─────────────────────────────────────────┐   │
│  │  - epd_app_register()                   │   │
│  │  - epd_page_create()                    │   │
│  │  - epd_service_*() (后台服务)           │   │
│  │  - epd_storage_*() (文件访问)           │   │
│  │  - epd_http_*() (网络请求)              │   │
│  │  - lvgl_*() (LVGL 对象)                 │   │
│  │  - rt_thread_*() (RT-Thread API)        │   │
│  └─────────────────────────────────────────┘   │
│                                                 │
│         平台固件 (HCPU)                         │
└─────────────────────────────────────────────────┘
```

## 理由

### 为何选择动态加载而非静态编译

#### 优势 1：存储灵活性

**静态方案的问题**：
- 所有应用占用内部 Flash 的固定空间
- 即使用户不用某个应用，代码也常驻 Flash
- 4.625 MiB 文件系统需要为固件预留大量空间

**动态方案的优势**：
- 用户按需安装应用
- 笔记、音乐等大型应用可选择安装到 TF 卡
- 内部 Flash 只需保留核心应用（如书架）

**实际数据**（典型应用大小）：
- 书架 (books): ~800 KiB
- 笔记 (notes): ~600 KiB
- AI 对话 (ai_demo): ~400 KiB
- 音乐 (music): ~500 KiB
- 天气 (weather): ~300 KiB

全部预装需要 ~2.6 MiB，占用超过一半文件系统空间。

#### 优势 2：更新灵活性

**静态方案**：
- 修复一个应用的 bug 需要重新编译整个固件
- 用户必须通过 USB 或 OTA 刷写完整固件
- 风险高（刷写失败可能变砖）

**动态方案**：
- 应用独立更新，只替换 `.sap` 包
- 可通过网页管理界面上传新版本
- 固件更新和应用更新解耦

#### 优势 3：开发效率

**静态方案**：
- 多人开发不同应用时，固件构建配置容易冲突
- 每次修改需要完整重新编译固件（耗时）

**动态方案**：
- 应用独立构建，只需要链接平台导出符号
- 开发者修改应用后，只重新打包 `.sap`
- 通过网页管理上传测试，无需烧录器

#### 优势 4：用户自定义

**静态方案**：
- 用户只能使用固件预装的应用

**动态方案**：
- 未来可支持第三方应用（需要应用审核机制）
- 用户可实验性安装社区开发的应用

### 为何共享地址空间而非隔离进程

**考虑过但未采纳**：独立地址空间的进程模型（如 Linux 进程）

**未采纳原因**：

1. **硬件限制**
   - SF32LB57 没有 MMU（内存管理单元）
   - 无法实现虚拟地址空间隔离
   - MPU（内存保护单元）功能有限，不支持完整进程隔离

2. **性能开销**
   - 进程切换需要保存/恢复大量上下文
   - 跨进程通信（IPC）开销大
   - 墨水屏应用对响应速度敏感

3. **资源占用**
   - 每个进程需要独立的页表和内核栈
   - 16 MiB PSRAM 无法支撑多个隔离进程

**共享地址空间的权衡**：

- **优点**：
  - 调用平台接口无需系统调用，延迟低
  - 内存管理简单，无需页表
  - 适合嵌入式 RTOS 的线程模型

- **缺点**：
  - 应用崩溃可能影响平台稳定性
  - 应用可访问平台内部数据结构（依赖代码质量）

**风险缓解措施**：
- 应用由平台开发团队维护（非完全开放的第三方生态）
- 构建时检查应用导入符号是否合法
- 运行时通过模块引用和资源管理防止野指针

### 为何选择 ELF 而非自定义格式

**ELF（Executable and Linkable Format）优势**：

1. **工具链支持**
   - GCC 直接生成 ELF
   - 现有调试工具（GDB）支持

2. **符号解析成熟**
   - ELF 的重定位机制标准化
   - RT-Thread 已实现 ELF 加载器

3. **避免重复造轮子**
   - 自定义格式需要实现解析器、加载器、符号绑定
   - ELF 经过广泛验证

## 后果

### 正面影响

1. **用户体验提升**
   - 按需安装，节省存储空间
   - 应用独立更新，降低更新风险

2. **开发效率提升**
   - 应用独立构建和测试
   - 减少固件构建冲突

3. **可维护性提升**
   - 应用 bug 修复不影响其他应用
   - 版本管理更清晰

### 负面影响与应对

#### 1. 应用崩溃影响平台稳定性

**风险**：
- 应用野指针可能破坏平台数据结构
- 应用死循环可能阻塞工作线程

**缓解措施**：
- 应用由核心团队开发和审核
- 受管服务框架提供超时和取消机制
- 关键平台数据结构通过接口访问，不直接暴露

#### 2. 符号冲突风险

**风险**：
- 多个应用使用的第三方库符号冲突
- 应用内部符号污染全局命名空间

**缓解措施**：
- 应用公共库（如 HTTP、JSON）由平台统一导出
- 应用私有符号通过 `static` 或命名空间前缀隔离
- 构建工具检查符号表，警告潜在冲突

#### 3. 加载时间

**风险**：
- ELF 解析和重定位需要时间
- 大型应用（如笔记 600 KiB）首次加载可能需要 1-2 秒

**缓解措施**：
- 显示加载动画，给用户反馈
- 常用应用（如书架）可预装并预加载
- 后台应用（如天气）启动时用户无感知

#### 4. 内存碎片

**风险**：
- 频繁安装/卸载应用导致 PSRAM 碎片化

**缓解措施**：
- 模块代码段在首次加载后保持，直到明确卸载
- 内存压力协调器优先回收数据，不频繁卸载代码
- 重启可清理碎片（嵌入式设备重启成本低）

## 实现细节

### 应用清单示例 (`manifest.json`)

```json
{
  "id": "books",
  "name": "书架",
  "version": "1.2.0",
  "platform_version": "1.0.0",
  "description": "电子书阅读应用",
  "author": "Platform Team",
  "icon": "icon.png",
  "entry": "libbooks.so",
  "background": false,
  "permissions": [
    "storage.read",
    "storage.write",
    "network.http",
    "audio.play"
  ],
  "data_version": 1
}
```

### 构建流程

```
应用源码 (C/C++)
    ↓
GCC 编译为 ELF 共享对象 (-fPIC -shared)
    ↓
工具检查符号表 (tools/check_app_symbols.py)
    ↓
打包为 .sap (tools/pack_app.py)
    - 主模块 (ELF)
    - 资源文件
    - manifest.json
    ↓
安装到设备 (网页管理或预装)
```

### 安装流程

```
1. 接收 .sap 包 → 写入临时目录
2. 解包并验证清单
3. 检查平台版本兼容性
4. 检查依赖符号是否可用
5. 验证文件记录和内容签名
6. 检查数据版本（更新场景）
7. 移动到正式安装目录
8. 登记应用入口
9. 通知桌面刷新图标
```

### 卸载与数据保留

- **卸载应用**：删除 `/flash/apps/<id>` 或 `/sdcard/.epd/apps/<id>`
- **保留数据**：`/flash/data/<id>` 或 `/sdcard/.epd/data/<id>` 不删除
- **重新安装**：应用检查数据版本，兼容则复用，不兼容则提示迁移或重置

## 对比：静态编译方案

如果采用静态编译，系统会是什么样？

| 方面 | 动态应用（已采纳） | 静态编译（未采纳） |
| --- | --- | --- |
| **固件大小** | HCPU 固件 ~3 MiB | HCPU 固件 ~5 MiB（包含所有应用） |
| **应用更新** | 独立更新 `.sap` | 重新刷写整个固件 |
| **存储占用** | 按需安装 | 所有应用占用 Flash |
| **用户选择** | 可选择安装哪些应用 | 无选择，全部内置 |
| **开发效率** | 应用独立构建 | 修改任意应用需重新编译固件 |
| **内存占用** | 只加载使用的应用 | 所有应用代码常驻（或需要复杂的按需加载） |
| **崩溃影响** | 应用崩溃可能影响平台 | 同样问题（共享地址空间） |
