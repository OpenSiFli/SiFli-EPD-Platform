# 内存与存储

平台将时间敏感的控制数据与大容量业务数据分开分配。片上 SRAM 支撑内核及有硬件约束的数据，PSRAM 容纳应用、图像、阅读缓存和计算工作区。Flash 保存程序、资源与持久化文件。当前没有把任意运行中对象自动换出到 Flash 的机制。

## 内存区域与所有权

| 区域 | 用途 | 分配与释放责任 |
| --- | --- | --- |
| HCPU SRAM | 内核对象、控制结构、硬件要求的工作区与部分线程栈。 | 内核、驱动或创建对象的模块释放。不能通过增加阅读缓存挤占此区域。 |
| HCPU PSRAM 分区，13.5 MiB | 应用模块、大块业务数据、图像和阅读缓存。 | 实际应用池需扣除静态区及其他专用堆；应用使用 `epd_app_alloc` / `epd_app_free` 配对管理。 |
| LVGL 专用堆 | 控件、布局及 LVGL 内部对象。 | 用 LVGL 对象生命周期和分配器管理，不能与应用内存释放接口混用。 |
| ACPU PSRAM 分区，2.5 MiB | 解码、字体、排版组件的私有上下文及工作区。 | 组件预算与公共计算调度共同约束，CLOSE 时释放。 |
| ACPU 片上 RAM，64 KiB | ACPU 固件运行所需的片上数据。 | 由配套链接配置划分。 |
| 跨核共享缓冲 | 请求、输入输出、页面像素的跨核访问。 | HCPU 客户端拥有，ACPU 在约定生命周期内借用；完成缓存同步后才能换所有者。 |

地址和容量以 源码：`project/sf32lb57-epd-gyd7n6_hcpu/ptab.json` 为准。分区容量、某个内存池的空闲量和可分配的最大连续块是不同指标，不能只根据 PSRAM 总剩余量判断一次大块分配一定成功。

`epd_app_alloc(..., EPD_APP_PSRAM)` 失败时返回空指针，不回退占用 SRAM。`realloc` 成功前保留原指针，释放仍使用同一分配体系。接口用法见[应用内存](../development/application-memory.md)。

## 预算与优先级

阅读缓存上限分别为排版 2 MiB、图片 2 MiB、页面帧 6 MiB，并保留应用可用内存余量；这些上限按需使用，不构成静态预留。文档转换的 ACPU 私有预算最多 1 MiB，字体远端会话最多 704 KiB（含远端状态、16 KiB 协作线程栈、控制结构预留和算法分配）。共享输入输出另计，因此不能只相加组件私有预算来推算整机峰值。

发生分配压力时，阅读器先释放窗口外缓存，再请求平台回收后台服务。平台排除前台应用、正在被调用的服务和没有声明可回收的服务。音乐播放等仍在工作的业务通过服务引用和活动保持受到保护；平台没有按应用名称强制杀进程的机制。

当前明确接入可回收声明的后台应用是天气。其他应用必须通过受管服务的 `epd_service_set_reclaimable()` 接入，且在回收前完成保存。未接入的后台内存不会被强行释放。

| 回收阶段 | 平台行为 | 结束条件 |
| --- | --- | --- |
| 请求 | 记录需要的可用量、请求序号和是否由实际分配失败触发。 | 当前容量已满足时直接返回；超过池容量的请求直接结束。 |
| 选择 | 逐步寻找声明可回收的后台服务，跳过前台和在途使用者。 | 找到候选或已无候选。 |
| 保存与停止 | 请求 flush，确认没有新的业务、调用和保护引用，再停止服务。 | worker、UI 清理和模块引用全部结束才算真正释放。 |
| 完成 | 检查空闲量。 | 达到目标、候选耗尽或五秒超时。结果分别报告。 |
| 恢复 | 空闲量达到带余量的水位并稳定后，允许后台重新装载。 | 避免刚释放就立即恢复，形成反复装载。 |

实现见 源码：`src/platform/app_memory_pressure.c` 与 源码：`src/services/app_service.c`。状态为“已请求停止”不表示内存已经释放。

## 文件布局

| 内容 | 内部存储 | TF 卡 |
| --- | --- | --- |
| 应用程序与资源 | `/flash/apps/<id>` | `/sdcard/.epd/apps/<id>` |
| 应用标准业务数据 | `/flash/data/<id>` | `/sdcard/.epd/data/<id>` |
| 应用可重建缓存 | 通过 `storage_app_path` 的缓存类别取得。 | 通过相同接口按安装卷取得。 |
| 笔记库 | 应用程序可安装在内部存储。 | 笔记业务库固定在 `/sdcard/Notes`。 |
| 日历提醒 | `/flash/system/reminders/calendr.bin` | 安装在 TF 卡也沿用该系统记录。 |

程序路径和业务数据路径不要求相同。卸载应用保留业务数据的规则只适用于安装器负责的目录，具体应用还可能使用上表列出的专用路径。完整应用操作见[应用使用手册](../user/application-guide.md)。

## 文件版本、锁和持久化

公共存储锁保护一次必要的文件操作及发布动作；分段复制、转换、校验和内存解析不会整段占住公共锁。应用保留存储会话和文件版本，在下一段操作前检查是否仍有效。文件签名可与文件修改版本绑定复用；外部改写、重新挂载和替换后，旧验证结果不再直接使用。

设置先在内存中生效，由串行后台任务保存，失败状态回传界面。需要原子替换的记录先写临时文件，检查写入与同步结果，再发布正式文件。保存完成前关机流程需要等待 flush，界面不能把“接受了保存请求”当作已经落盘。

字体导入分段复制时同时计算内容签名；完整校验属于新字体安装流程。已安装字体启动时利用安装记录、大小及关键头部执行轻检查。轻检查不能发现所有大小和头部都未变的离线改写；实际解析仍会报告读取或格式错误。

## TF 卡与 USB 所有权交接

1. 开启读卡器或拔卡时，平台使旧 TF 卡会话失效，禁止新任务继续使用旧路径。
2. 应用停止相关请求、关闭文件、退出需要 TF 程序的页面，并释放程序引用。后台完成后由界面维护步骤结束清理。
3. 卡上文件系统退出本机使用后，USB 大容量存储才接管块设备；USB 工作期间持有电源约束。
4. 关闭读卡器后停止 USB 访问，重新挂载 TF 卡，产生新的会话和文件有效性状态。
5. 用户确认加载卡上应用后才发布对应应用入口。锁屏期间不弹出该确认框，解锁后再处理有效请求。

等待旧使用者退出期间保留保护引用，不能因为等待超时就强制释放。迁移某个应用的数据失败只限制该应用，其他正常应用及卸载入口仍可用。发生持续存储故障时按照[问题排查](../troubleshooting/troubleshooting.md)确认状态，再决定重插卡或恢复。

主要接口与实现：源码：`src/services/storage.h`、源码：`src/services/storage_file.c`、USB 读卡器（源码：`src/services/usb_card_reader.c`）、应用安装器（源码：`src/ui/platform/`）。
